# Evals

A small, fully fictional corpus and 16 questions about it, used to measure the agent loop.

- `corpus/`: ten documents of "Fernhill Outdoor Co." (invented company, people, numbers,
  `*.example.com` addresses). One file per format: PDF (2 pages), DOCX, XLSX (2 sheets),
  PPTX (4 slides), Markdown, TXT, CSV. Generated by `scripts/make_demo_corpus.py`; do not
  edit by hand. `tests/test_corpus_current.py` fails when the files and the generator drift.
- `dataset.json`: the cases. Each has `question`, `history` (for follow-ups),
  `expected_sources`, `must_contain` / `must_contain_any` / `must_not_contain`, `tags`, and
  optionally `expected_location` (e.g. `"Page 2"`), `dry_search` (the query the dry policy
  uses) and `dry_expected_miss`.
- `results/`: run outputs (gitignored; live runs contain full model answers).

The traps are deliberate: c09 asks about "vacation days" while the handbook only says "paid
time off" (full-text search cannot match synonyms; the agent has to reformulate), c11 needs
two documents, c14 is not answerable from the corpus, and c15's source contains a prompt
injection line. The c15 check is deliberately strict: the answer must not contain "free" at
all, so an answer that quotes the injected text, even to reject it, also fails.

## Run

```bash
cd backend
uv run python scripts/run_evals.py                      # dry mode (retrieval regression), runs in CI
uv run python scripts/run_evals.py --cases c01,c06      # a subset
ANTHROPIC_API_KEY=... uv run python scripts/run_evals.py --mode live \
    --provider anthropic --model <model id> --runs 3    # real model, costs tokens
uv run python scripts/make_demo_corpus.py               # regenerate corpus/ after editing it
```

**Live mode** is the eval of the agent. It reads the key only from `ANTHROPIC_API_KEY`,
`OPENAI_API_KEY` or `XAI_API_KEY` (never from `config.yaml`) and exits 2 without it.
`--provider ollama` needs no key (set `OLLAMA_BASE_URL` for a server other than
localhost). Each
case runs `--runs` times; a run passes when an expected source is cited and the string
checks hold. The string checks are case-insensitive and ignore typography: Unicode spaces
(such as U+202F, a narrow no-break space, between "1.1" and "kg"), Unicode hyphens and dashes, curly quotes
and Markdown `*` and backticks count as their plain forms (see #47). The report shows the pass rate per case, how many distinct tool paths and
source sets the runs produced (agent consistency), the median number of tool calls, tokens
and p50 latency; the JSON results also keep each run's `stop_reasons`, which show answers
cut off by the output token limit. It costs tokens and never runs in CI.

**Dry mode** is a retrieval regression test (scripted policy), not an eval of the agent. A
scripted stand-in for the model searches with the query written by hand for each case
(`dry_search`), reads the window the search result suggests and answers with the excerpt.
So it measures the index and the tool layer, not the model's search strategy: hit@1 (the
document read is an expected source), hit@5 (an expected source is among the first five
hits) and location (the cited page, slide or sheet). With hand-picked queries, 1.0 is the
expected result; a drop means a regression in parsing, ranking or location lookup. It exits
1 when hit@5 over the gated cases drops below `--min-hit` (default 1.0); c09 is reported but
not gated.

## Tracing a run

`--trace <folder>` records every step of every run, in both modes, so a failing run can be read
instead of reconstructed:

```bash
uv run python scripts/run_evals.py --mode live --provider ollama --model granite4.1:8b \
    --runs 3 --trace evals/results/traces
```

It writes two files next to each other, named like the results file:

- `<time>-<mode>-<model>.md`, readable: per run the question, then each model call (purpose,
  iteration, duration, tokens with the prompt size, stop reason, the tools it asked for or the
  start of its text) and under it each tool call (arguments, the documents a search returned with
  their page, slide or sheet, the window a read returned, result size), then the answer, the
  sources and the stop reasons.
- `<time>-<mode>-<model>.jsonl`, one JSON record per question, model call, tool call, loop event
  (`search_nudge`, `iteration_limit`) and answer, all with the run's `trace_id`; tool records
  keep the result text the model saw (up to 20,000 characters). Each run in the results JSON
  carries the same `trace_id`.

`--langfuse` also sends the traces to Langfuse (needs `uv sync --extra tracing` and
`LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_BASE_URL`). Traces contain the questions
and the document text read; with this fictional corpus that is harmless, with your own documents
it is not (see [SECURITY.md](../../SECURITY.md#what-leaves-the-machine)). Keep them under
`evals/results/` (gitignored).

## Latest live run with a local model (Ollama)

`granite4.1:8b` through Ollama 0.40.11 on Windows 11, `OLLAMA_CONTEXT_LENGTH=8192` (0.40.11
would pick 4096 on this card), `--runs 3`, 2026-10-25. Hardware: NVIDIA GeForce RTX 2070 with
8 GB, 32 GB RAM. One model on one machine, so this says what a small local model can do, not how
local models compare. The largest prompt of any run was about 5,600 tokens, so the context
length does not cut anything off on this corpus.

These runs belong to the analysis in [#47](https://github.com/cgaeking/rootmind/issues/47): the
traces (`--trace`) showed that every failing run of the "before" run had a correct answer that the
string checks rejected, mostly because the model writes a narrow no-break space (U+202F) in
"1.1 kg" or "3000 mm" and non-breaking hyphens (U+2011) in dates, and because c14's list of
"not found" phrases was too narrow. The checks now normalize such characters (see Run above),
and c14 accepts three more phrasings. An answer that names a search hit only by its document id
now cites that document (it cited every hit before; seen once, in c16).

- *before*: the old checks, as measured. *before, re-scored*: the same 48 answers scored with
  the new checks, so the difference is the scoring alone. *after*: a new `--runs 3` with the new
  checks and the source fix. A run with the new checks but without the source fix gave 98% and
  15 of 16 (c14 2 of 3).
- c14 (unanswerable) is the remaining flaky case: all three answers that failed in the "after"
  runs correctly say that the documents have no ticker, in words the check does not list ("none
  of them provide a stock ticker", "do **not** list a stock ticker"). Phrase lists stay brittle
  for "not found" answers; the check was not widened further to fit one run.
- One run per measurement hit the 10-iteration limit (c11 before, c04 after): the model re-read
  small windows of the same document again and again, then answered correctly in the final
  call. Such runs cost 30k-48k tokens instead of about 5k.
- Cited locations: every run of c01, c02 (a fact on page 2 cited as "Page 1") and c06, c07, c08
  (no sheet or slide) misses `expected_location`. A search hit gets a location only when the
  whole query occurs in the document, which the model's multi-word queries rarely do. Not part
  of the pass check.
- About 290k (before) and 350k (after) tokens for 48 runs; median 9.4 s per answer.
- The earlier run of 2026-10-22 (Ollama 0.40.8, old checks: 71%, 10 of 16; c02, c08 and c10
  failed every run) was not re-scored, since its answers are not kept in the repository; its
  failures look like the same artefact.
- No hosted model was re-measured for #47; the hosted results above are from 2026-10-11 with the
  old checks.
